## 5. 결정할 것과 주의

- **즉시 재스캔 vs ADR-0002 4조.** 4조는 "트리거는 payload 없이 허용목록 키만"이다. 플레이어 ID를 담는 재스캔과
  충돌한다. 검증된 정수 ID 하나만 큐 테이블에 쓰고 요청 형식은 코드가 만드는 방식이면 지킬 수 있다.
  ADR에 이 예외를 적는다.
- **스윕 범위.** 우리 8서버만 / 토요일 킬데이 서버 추가 (10-08 결정은 후자). 미정.
- **요청량은 가정.** 서버당 약 100요청은 중심부 밀도를 전체로 늘린 추정이다. 실측 전에는 믿지 않는다.
- **`CLAUDE.md`의 "지도 크롤러는 아직 안 만든다" 문장**은 크롤러를 실제로 만드는 PR에서 함께 고친다.
- 새 마이그레이션 번호는 push 시점의 `origin/main` 기준으로 잡는다.

## 6. 추가 요청 (2026-11-05)

### 6-1. 트럭·Dispatch Mission(plunder) 갱신 주기

**지금은 수동적이다.** 트럭은 `train.list`(가로챌 수 있는 트럭 목록), `get.train.info`, `push.world.march.new` type 15에서,
미션은 `world.get.new` 타일(type 21)에서 온다 (`normalize/world_trucks.py`, `world_map.py`). 전부 **누군가 화면을 열거나
서버가 푸시해 줄 때만** 들어오므로 갱신이 불규칙하다. 보존도 개체별 최신 1건뿐이다 (0299).

클라우드 부계정이 읽기 요청을 보내면(ADR-0002) 주기를 우리가 정한다.
- 트럭: `train.list`를 N분마다 요청. 이 명령이 요청 가능한지, 요청 shape이 무엇인지는 **요청 캡처에서 먼저 확인**(Phase 0).
  트럭은 도착 시각이 있어 수명이 짧다 → 짧은 주기가 의미 있다 (시작값 제안: 2~5분, 상한은 코드).
- 미션: `world.get.new`의 우리 서버 뷰포트를 훑어야 한다. 미션이 어느 구역에 있는지 모르면 한 바퀴가 비싸다.
  → 먼저 최근 관측 좌표로 **핫 구역만** 자주, 전체는 드물게.
- 대시보드: 지도 모드 Plunder에 "n분 전 읽음" 표시와 도착 카운트다운 (남은 시간이 지난 트럭은 자동으로 숨김).
- 알림(Phase 2-3과 묶음): 감시 플레이어나 황금 조각 최소 개수 조건으로 트럭 출발을 알린다.
- 막혀 있는 것: 부계정 로그인 핸드셰이크 (Phase 0). 이게 안 되면 부계정 `dw-ui-worker`가 화면을 열어 주는 방식이라
  주기가 훨씬 느리다.

### 6-2. 기프트 코드 — "클릭하면 게임이 켜지고 로그인되어 리딤"

**사실 확인 (`docs/runbooks/gift-codes.md`).**
- 리딤은 게임 프로토콜이 아니라 **공식 웹 Gift Center를 부르는 것**이고, 이미 `dw-gift`와 DB 발신기(0252)가 있다.
- 2026-10-10부터 요청마다 **플레이어별 `uuid` 키**가 필요하다. 게임 패킷 어디에도 없고, 플레이어가 받은 Gift Center
  링크에서만 나온다. 지금은 연맹원이 본인 링크를 붙여 넣어 저장한다 (0273).
- Gift Center 첫 화면(2026-11-05 확인)은 "Go to Official Mall"만 보인다. 로그인 방식이 QR인지는 **로그인 뒤 화면을
  봐야 알 수 있고 아직 못 봤다.**

**"클릭 → 다크워 자동 실행 → 리딤"은 반쪽만 된다.**
- 클라우드 봇이 켜는 게임은 **수집 계정의 것**이다. 연맹원 각자의 키는 그 사람 자신의 기기·로그인에서만 나온다.
  봇이 대신 얻을 수 없고, 얻으려 해서도 안 된다 (남의 계정 로그인).
- 그러므로 가능한 것: ① **수집 계정 본인의 코드 리딤**은 완전 자동 (봇이 키를 갖고 있으면 됨).
  ② 연맹원은 **키를 한 번만** 연결하고 이후는 자동 (지금 구조 + 만료 알림).

**QR 방식 (Vantera "게임 QR 로그인"을 따른다면).** 흐름은 보통: 웹이 QR을 보여 줌 → 플레이어가 **자기 게임에서 그 QR을
스캔** → 웹 세션이 그 플레이어로 로그인됨 → 키 확보. 우리가 할 수 있는 것은 웹 페이지나 Discord 봇이 그 QR을 보여 주고
플레이어가 스캔하는 부분까지이고, 스캔 자체는 사람이 한다. 전제 두 가지가 **미확인**이다.
1. 공식 Gift Center가 QR 로그인을 제공하는지, QR이 무엇을 담는지 (로그인 뒤 화면 확인 필요 — 사용자가 직접 해 주어야 함).
2. 그 QR 로그인으로 받은 토큰을 우리 서버가 저장해 재사용해도 되는지 (약관, 만료 시간).
확인되면: 대시보드에 "연결" 버튼 → QR 표시 → 스캔 완료 시 `gift_player_keys` 저장. Discord 봇 `/link`도 같은 QR을 보낸다.
확인 안 되면 현재의 링크 붙여 넣기를 유지하고 **UX만** 개선한다 (단계 안내, 만료 임박 표시, 한 번에 여러 캐릭터).

**자동 수령 옵션.** 새 코드가 생기면 키가 있는 사람에게 자동 큐잉하는 것은 지금 일부러 꺼 둔 기능이다 (런북 "자동 적용은
일부러 안 넣었다"). 사람이 켜는 설정으로 다시 열지는 사용자 결정이다. 코드 자동 발견(스캔)은 아직 없다.

### 6-4. 기프트 자동화 방향 수정 (사용자 지시)

**로그인은 전적으로 각자의 계정에서 한다. 우리 서버는 로그인도 키도 갖지 않는다.** 자동화하는 것은 로그인된 mall 페이지
아래 코드 리딤 입력과 제출뿐이다. 이전 작업(0251~0273, `gift/official.py`)은 서버가 사람별 `uuid` 키를 저장해 대신 `code.php`를
부르는 방식이었고, 이 방향은 그 저장을 없애는 쪽이다.

- 이전 작업에서 재사용: 호출 모양 `code.php?uid=&code=&uuid=&fromkoc=` + 헤더 `Usertoken`, `errorCode` 분류(ok / E004 / E005 / E006 / E007 / E009),
  속도 규칙(요청 사이 5~6초, 연속 `retry` 5회에 쉼, 보안 확인이 뜨면 멈춤).
- 새 구조(제안, 미검증): 사용자의 **자기 브라우저**에서 도는 유저스크립트/북마클릿이 mall 페이지 안에서 대시보드의 유효 코드
  목록을 받아 리딤 요청을 보낸다. `uuid`는 로그인된 페이지 주소에 이미 있으므로 스크립트가 거기서 읽고 **어디에도 저장하거나 보내지 않는다.**
  결과(받음/이미 받음/만료)만 대시보드에 보고할 수 있다.
- 대시보드의 "받기" 버튼은 mall 링크를 연다(코드는 주소가 아니라 스크립트가 가져온다). 서버 발신기(0252)는 끌 수 있다.
- **먼저 확인할 것(사용자 협조 필요):** 로그인된 mall의 리딤 화면 주소와 요청 하나(틀린 코드로 `Copy as cURL`, uid/uuid 가림).
  같은 출처(origin)에서 `code.php`를 부를 수 있는지, 스크립트가 허용되는지가 이 한 번으로 갈린다.
- 그 외: 약관은 여전히 미확인. 보안 확인(슬라이더 등)이 뜨면 우회하지 않고 멈춘다.
