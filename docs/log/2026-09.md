이 표는 한동안 「확인 안 됨」이었다. 세 줄 다 있는 것을 사용자가 운영에서 직접 확인했다:

```sql
select version, name
  from supabase_migrations.schema_migrations
 where version in ('20260728000175', '20260728000176', '20260728000177')
 order by version;
```

**이 질문은 세션에서 대신 답할 수 없다.** 운영 프로젝트의 URL과 키는 Cloudflare/GitHub
쪽에 있고 레포에는 없다(CLAUDE.md). `supabase` CLI도, `supabase/.temp/project-ref`도,
`.env`도 없다 — 세션이 볼 수 있는 것은 **파일이 main에 있다는 것까지**다. 그러니
「운영에 올라갔나」는 위 쿼리를 사람이 돌려야 하고, 그 답은 이렇게 날짜와 함께 적는다.

올리는 방법은 (14)와 같다 — **파일 전체 + 기록 행 `insert`를 `begin`/`commit` 하나로**.
한쪽만 하면 표의 「됨」이 거짓말이 된다: 기록 행만 넣으면 함수가 없고, 함수만 올리면
나중에 `db push`가 같은 파일을 다시 돌린다. 기록 행과 함수가 어긋났다고 의심되면
`pg_get_functiondef`로 본문에 `0177` 주석이 있는지 보면 된다.

순서는 (14)의 규칙이 이번엔 걸리지 않았다: 0175·0176·0177은 컬럼을 더하지 않고
함수와 뷰만 만든다(0176은 `capabilities` / `role_permissions`에 `data.enter` 행도
넣는다). 다만 **0176의 세 함수는 `create function`이라 재실행이 깨진다** — 기록 행을
빼먹으면 나중에 `db push`가 여기서 멈춘다.

### 0174의 실제 버그 — CHECK는 미루지 못한다 (#275, 0177)

0174가 넣은 `hive_pins_protect_somebody`(핀은 지킬 사람이 있어야 한다)는 규칙으로는
맞다. 문제는 **CHECK 제약이 deferrable이 아니라 행이 쓰이는 즉시 검사된다**는 것이다.
두 writer 모두 타일을 비우는 문과 핀을 내리는 문이 **따로**였고, 그래서 비우는 문
자체가 거부됐다:

```
new row for relation "hive_formation_slots" violates check constraint
"hive_pins_protect_somebody"
```

터지는 경우: 핀 걸린 멤버를 옮길 때, 교체할 때, 그리고 #273 이후로는 **핀 걸린 멤버가
연맹을 떠난 뒤 아무 저장이나 할 때마다**. 0177은 규칙을 그대로 두고
`assign_hive_formation_slots`와 `save_hive_formation_layout` 둘 다 **핀을 멤버와 같은
문에서** 내리게 고쳤다. 0173/0174와 나머지는 동일하다.

일반화해 둘 것: **한 문에서 만족시킬 수 없는 불변식을 CHECK로 쓰지 않는다.** 나중에
고치는 문이 있어도 그 문까지 가지 못한다.

## 2026-09-09 상태 (12) — 타입 생성을 `--local`로 통일했다

(9)부터 "남은 결정"으로 끌고 오던 것. 결론부터: **`--local`이 유일한 길이고,
`--linked`는 이제 도구가 거부한다.**

### 먼저, 내가 (10)에 적어둔 진단이 틀렸다

(10)의 남은 것에 "저장소 스크립트(`pnpm db:types`)가 `--linked`"라고 썼는데
**거짓이다.** `package.json`을 열어보지 않고 증상에서 추론해 적었고, 사용자에게
두 번 그렇게 말했다. `git log -L`로 확인하면 이 스크립트는 도입된 날부터
`--local`이었고 CI도 `--local`이다. 둘은 한 번도 갈린 적이 없다.

**진짜로 갈렸던 건 CI와 *운영자가 실제로 치던 명령*이다.** (7)에 그대로 적혀
있다 — Windows에 로컬 스택이 없어서
`supabase gen types typescript --linked --workdir C:\darkwar-platform`로
재생성했다고. 호스티드 프로젝트는 `__InternalSupabase` / `PostgrestVersion`
블록을 내고 로컬 스택은 안 내니까, 그렇게 만든 파일은 CI의 `--local` diff 검사에
아무도 손대지 않은 블록으로 걸린다.

증상만 보고 원인을 지목하면 이렇게 된다. **`package.json` 한 줄 여는 게
추론보다 쌌다.**

### 고친 것 둘

**1. `pnpm db:types`가 `scripts/db-types.mjs`를 거친다.**
`>` 리다이렉트는 명령이 실행되기 *전에* 파일을 비운다. Docker Desktop이 꺼져
있으면 CLI가 실패하는데 커밋된 타입 파일은 이미 비워진 뒤고, 운영자는 망가진
작업트리와 "아무것도 안 한" 명령을 앞에 두고 `--linked`로 손을 뻗게 된다. 그게
이 사고의 실제 경로다.

새 스크립트는 stdout을 받아 **검사한 뒤에만** 쓴다. 실패하면 아무것도 안 쓰고,
`--linked` 모양(`__InternalSupabase:` / `PostgrestVersion`)이면 그것도 거부한다.
실패 메시지가 `supabase start`를 시키고 `--linked`를 쓰지 말라고 명시한다.

**2. `pnpm test`가 커밋된 타입의 모양을 본다.**
`apps/dashboard/tests/generatedTypes.test.ts`. 손으로 고쳤든 머지로 들어왔든
CLI를 직접 쳤든, `--linked` 산출물이면 **커밋 전 루프에서** 걸린다 — `db` 잡
6분을 기다리지 않고. `web` 잡의 path 필터가 `packages/**`를 포함하니 CI에서도
탄다.

주의: `Omit<Database, "__InternalSupabase">`는 `--local`도 내는 정상 보일러플레이트다.
그래서 이름이 아니라 **선언**(`__InternalSupabase:`)을 본다. 이름으로 매칭하면
멀쩡한 파일이 빨개진다.

둘 다 무의미한 단언이 아닌지 확인했다 — 가짜 `__InternalSupabase` 블록을 넣어보고
테스트가 실제로 실패하는 것, 그리고 스택 없이 스크립트를 돌렸을 때 타입 파일이
`git diff` 기준 그대로인 것을 봤다.

### 그래서 Windows에서 할 일

타입을 재생성할 일이 생기면 **Docker Desktop을 켜고** `supabase start` 뒤에
`pnpm db:types`. 스택이 없으면 재생성하지 말고 그냥 두면 된다 — 스크립트가
파일을 망가뜨리지 않는다.

### A — 타일이 제 크기·종류·색을 갖는다 (0169, 0170)

0165는 전부를 숫자 하나 위에 지었다. 베이스는 3x3이니 배제 제약이
`int4range(dx - 1, dx + 2)`였고, 프랭키(4x3)를 피하려고 프런트엔드가

0169가 크기를 행으로 옮기고 제약이 그걸 읽는다. 프랭키는 특수 케이스가 아니라
`span 4x3, kind='structure'`인 평범한 타일이 되고, 연맹 건물과 1x1 마커는 같은
것의 다른 크기가 된다.

**짝수 span의 좌표 규약은 적어둔다.** `low = dx - (span - 1) / 2` (정수 나눗셈).
3이면 가운데, 4면 **가운데 두 열 중 서쪽**, 1이면 그 타일 자신. SQL과 TypeScript가
같은 식을 쓴다. 프랭키의 어느 열이 게임 좌표인지는 확인 못 했으므로 서쪽으로
가정했고, 틀렸다면 화면에서 보이도록 사각형을 그린다.

### 87: 0065가 SELECT만 회수했다

```sql
alter default privileges in schema public revoke select on tables from anon;
```

Supabase 기본값은 anon에게 **네 개**를 준다. 하나를 빼면 **셋이 남는다** —

## 2026-09-08 상태 (8) — 하이브 포메이션: 타일 배정 (0165~0167 + 프론트)

### 요청 — "맹원들이 자기 멋대로 텔포해서 줄이 안 맞는다"

하이브 이동이나 전쟁 집결 때 베이스가 정렬이 안 되는 건 의지 문제가 아니라
**할 수 있는 방법이 없어서**다. 채팅으로 "여기로 모여"를 말하면 84명이 각자
비어 보이는 타일을 고르고, 게임은 좌표 하나만 보여준다. 그 좌표가 실제로는
**9칸**이라는 사실이 어디에도 안 적혀 있다.

**베이스는 3x3이고 좌표는 그 한가운데다.** 이 한 문장이 이 기능 전체의
근거다. 맵은 한 칸 단위로 주소가 매겨지므로 `500,500`과 `501,500`은 서로 다른
두 칸의 이름이면서 **같은 땅**이다. 둘 다 배정받으면 두 번째 사람은 텔포가
안 되고, 그 사실을 여기가 아니라 게임 안에서 알게 된다.

### 0165 — 겹침을 DB가 거부한다

중심 좌표가 **두 축 모두에서 3칸 미만**이면 겹친다. 한 축만 가까운 건 겹침이
아니라 **꽉 찬 하이브**이고 그게 원하는 모양이다. 이걸 규칙이 아니라
exclusion constraint로 들고 있다:

```sql
exclude using gist (
  formation_id extensions.gist_uuid_ops with =,
  (int4range(dx - 1, dx + 2)) with &&,
  (int4range(dy - 1, dy + 2)) with &&
)
```

`btree_gist`가 uuid `=` 때문에 필요하고, opclass는 search_path에 기대지 않게
스키마를 붙여서 적었다.

**슬롯은 절대 좌표가 아니라 앵커로부터의 오프셋으로 저장한다.** 하이브는 한 번
그리고 여러 번 옮긴다 — 84칸을 옮기는 게 한 행 수정이고, 모양이 안 변한다는 게
증명된다. 부수 효과로 **겹침 판정이 오프셋만의 성질**이 된다(앵커는 상수라
소거된다). 그래서 위 제약이 dx/dy만 보고도 땅에 대해 참이다.

3x3이 맵 밖으로 나가는 경우는 check constraint로 못 잡는다(슬롯은 부모의
앵커가 필요하고, 앵커는 모든 자식이 필요하다). **트리거 두 개, 함수 하나**로
양쪽에서 본다. 앵커 이동이 84칸을 한꺼번에 맵 밖으로 밀어내는 유일한 연산이라
그쪽이 특히 필요했다.

### 0166 — 좌표 덧셈은 서버에서 한 번만

`hive_formation_board`가 `anchor + offset`을 한다. 브라우저에서 더하면 이
기능이 내놓는 유일한 숫자가 클라이언트 계산 뒤에 숨고, 캐시에 낡은 앵커가
있으면 84명이 엉뚱한 땅으로 간다.

`still_a_member`는 **`alliance_roster_latest`로** 본다. 저장소 상시 규칙 그대로
`players.current_alliance_id`는 아무도 안 지우므로 항상 "예"라고 답한다. 2주 전
포메이션에 탈퇴자가 배정돼 있는 걸 알려주는 게 이 컬럼의 존재 이유라서 거기서
읽으면 의미가 없다. EXISTS라 슬롯당 한 행이 유지된다.

### 0167 — 저장 단위는 "포메이션 전체"

0165의 제약 때문에 **부분 쓰기가 불가능하고, 그게 맞다**:

- 모양을 동쪽으로 한 칸 밀면 새 슬롯이 전부 옛 슬롯과 겹친다. insert→delete는
  첫 행에서 거부되고, delete→insert는 그 사이에 아무것도 안 끼어야 한다.
  PostgREST로는 두 요청 = 두 트랜잭션이다.
- 두 명 자리 바꾸기는 `hive_slot_one_place_per_member`가 **어느 순서로 해도**
  중간 상태에서 거부한다.

그래서 `save_hive_formation_layout` / `assign_hive_formation_slots` 두 함수가
한 트랜잭션에 통째로 쓴다. 살아남은 타일의 배정은 유지되고, 사라진 타일 때문에
자리를 잃은 인원 수를 결과로 돌려준다.

**temp table을 쓰지 않는다.** `set search_path = ''`면 pg_temp가 안 잡히고,
함수 안에서 만든 temp table은 같은 트랜잭션 안 두 번째 호출에서 터진다 —
테스트 스위트가 정확히 그 모양이다. `jsonb_to_recordset`을 문장마다 다시 편다.

### 처음으로 pgTAP을 실제로 돌렸다

(7)에서 "Docker가 없어서 0149~0157이 한 번도 실행되지 않았다"고 적어둔 그
pgTAP이다. 이번 세션 컨테이너에는 로컬 PostgreSQL 16과 `postgresql-16-pgtap`이
있어서 **`91_hive_formation_test.sql`을 31 단언 전부 초록으로 돌렸다.**

**단, 스텁 스키마 위에서다.** 마이그레이션 체인 전체가 아니라
`servers`/`players`/`app_users`/`current_app_role`/`has_permission` 등을 실제
정의대로 흉내 낸 최소 스키마 위에 0165~0167만 얹었다. 그래서 이 파일의 문법과
단언은 검증됐지만, **다른 마이그레이션과의 상호작용은 여전히 미검증**이다.
Docker 있는 머신에서 `supabase test db`는 그대로 남은 숙제다.

돌리는 법(재현):

```
su postgres -c "PATH=/usr/lib/postgresql/16/bin:\$PATH initdb -D <dir>/data -U postgres -A trust"
# 스텁 + 0165~0167 적용 후
su postgres -c "PGOPTIONS='-c search_path=public,extensions' psql ... -f supabase/tests/91_hive_formation_test.sql"
```

pgTAP은 `extensions` 스키마에 들어가므로 `search_path`에 넣어야 `plan()`이
보인다. 그거 하나로 31개가 전부 "function plan(integer) does not exist"였다.
