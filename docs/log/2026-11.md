## 2026-11-18 — 게임 1.250.672: datatable이 Lua 5.5가 되어 `game-catalog`·`game-names`·`game-values`가 읽지 못했다

요청: "`decode()`가 옛 형식(5.4)과 새 형식을 버전 바이트로 구분해 둘 다 읽게, 두 형식 모두 단위 테스트, PR."
맥 세션이 먼저 잰 것: 새 파일은 `1b 4c 75 61 a8 55 …`, `a8`을 빼면 헤더가 `lupa.lua55` 덤프와 같은데
로드하면 `bad binary format (invalid constant)`.

- **원인 둘.** (1) 5.5는 코드 벡터와 절대 줄 정보 앞을 청크 첫 바이트부터 센 4바이트 경계로 채우는데,
  클라이언트는 표식 `0xa8`까지 세서 채웠다. 표식만 빼면 패딩이 1바이트 어긋나 상수 태그 자리에 명령어
  바이트가 온다 — 그게 "invalid constant"였다(상수 태그 재매핑이 아니었다; 태그는 표준 그대로).
  청크 3,378개 전부 "파일 시작 기준 정렬"로 EOF까지 정확히 읽힌다. (2) **opcode가 재번호돼 있다.**
  첫 명령이 스톡은 `0x53`(VARARGPREP), 클라이언트는 `0x22`. 번호가 116종 쓰여 85개 opcode의 단순
  순열도 아니다 — 0..84가 순열, 85..127이 별칭.
- **번호표는 `libxlua.so`(x86_64) 정적 분석으로 읽었다.** 로더는 표준(번호를 안 바꿈). `luaV_execute`의
  디스패치 표(RELATIVE 재배치 128개, 대상 85개)와 vmfetch가 거치는 별칭 표(0..84 그대로, 85..127 →
  대표), 그리고 핸들러 16개의 기계어(LOADF의 `cvtsi2sd`+태그 0x13 등)로 판정. 근거 표는 런북
  "Lua 5.5 datatable". 핸들러 주소 순서가 소스 순서라는 가설은 틀렸다(컴파일러 재배치). 클라이언트의
  `luaP_opmodes`로 교차 검증하려 했지만 표준 비트 배치의 표가 바이너리에 없어 못 했다 — 대신 실데이터로
  검증(아래). 도구는 저장소 밖 `C:\DW_data\lua55\`(`read_opcodes.py`, README).
- **`luatable.py`**: `stock_bytecode()`가 시그니처 다음 바이트로 표식 유무를, 그다음 바이트로 버전을
  가른다. 5.4(`\x03`)는 예전대로 `lupa.lua54`. 5.5는 표식별 번호표(`CLIENT_OPCODES[0xa8]`)로 필드 단위
  재작성(패딩 재계산 + 하위 바이트 `bytes.translate`)한 뒤 `lupa.lua55`로 돌린다. 매핑은
  datatable에 필요한 16개만이고 **다른 번호는 실행하지 않고 거부**, 모르는 표식·표식 없는 5.5도 거부.
- **검증.** 1.250.672 datatable 479개 전부, 214,268행, 12초. 테스트 `test_luatable.py`: 직접 쓴 테이블을
  5.4+`\x03`과 5.5 클라이언트 형식(표식·패딩·재번호, 별칭 포함)으로 만들어 같은 결과, 5.5 재작성이
  lupa 원본 덤프와 바이트 단위로 같음, 두 정렬 지점(코드·절대 줄 정보) 모두, 매핑 밖 번호·모르는 표식·
  잘린 청크 거부. 게임 파일은 커밋하지 않았다.
- **DB 대조 (쓰기 전, 읽기만).** 새로 읽은 카탈로그와 그때 `game_upgrade_steps`(5.4 시절에 올린 17,890행)를

  새 값 64개 주제, 11-09 정정 뒤 임포터를 한 번도 안 돌린 탓). 새 행은 연구 353·칩 200·건물 1.
  `game_items` 1,869개 이름 전부 같고 32개 추가.

  읽기만).** `game-catalog --bundles base --bundles bundles` → `items=1901 resources=24 steps=18444
  {building 10697, research 4844, vehicle_part 396, vehicle 499, pet 306, pet_break 31, hero 199,

## 2026-11-17 ~ 11-18 — 게임 1.250.672: 압축 응답이 APS zstd v1로 바뀌어 수집기가 전부 버리고 있었다

요청: "`al.rank`, `init`, `world.get.new` 본문이 고엔트로피라 세션 키가 필요해 보인다, 도와줘"
(내 트래픽 읽기만. 안티치트 우회·요청 위조 아님).

- **증상.** 11-17 10:50 업데이트 뒤 서버→클라 압축 프레임(0x20)이 zlib이 아니게 됐다. 디코더는 본문
  첫 2바이트가 zlib 헤더가 아니라서 resync 바이트로 넘겼고, `al.rank`·`world.get.new`·`get.al.info`·
  로그인 응답 같은 **압축 응답이 저널에 하나도 안 들어갔다.** 평문 프레임(push 대부분)과 요청은 그대로라
  ingest 로그는 건강해 보였다.
- **형식** (클라이언트 `Sfs2X.Util.ApsZstdCodec`·`ApsZstdV1` 디스어셈블에서 읽음): `nonce(8) || 매직 4바이트를
  뺀 zstd 프레임`, 앞 `min(128, len−8)`바이트를 `AES-256(SHA256(키), nonce‖be64(i))`로 XOR — nonce‖0에서
  시작하는 AES-CTR과 같다. nonce는 연결마다 1씩 오른다(사용자가 본 "카운터").
- **키는 세션 키가 아니라 APK 상수다.** `NetworkManager.ResolveApsZstdV1Key`가 `<PrivateImplementationDetails>`의
  32바이트 블롭을 ASCII 리터럴로 XOR해 Base64로 만든다. 계정·세션과 무관. 정적 분석만 했고(IL2CPP
  메타데이터 v31 + `libil2cpp.so`), 실행 중 프로세스·루팅·Frida는 안 썼다. 추출기와 순서는 저장소 밖
  `C:\DW_data\aps\` (`README.md`), 키는 `C:\DW_data\aps_zstd_v1_key.txt` — **커밋하지 않는다.**
- **수집기** (`protocol/aps_zstd.py`, `frames.py`, `pcapng.py`): 압축 본문은 zlib처럼 시작하고 풀리면 zlib,
  아니면 APS(옛 캡처도 그대로 재생된다). 가짜 헤더는 첫 24바이트(nonce + AES 한 블록)로 zstd 프레임 헤더와
  첫 블록 헤더를 읽어 길이를 기다리기 전에 거른다. 하루치 실제 프레임 11,306개는 디스크립터가 `0x60`·`0xA0`뿐,
  복원 최대 470,895바이트(로그인), 본문 최대 85,870바이트(`MAX_FRAME_SIZE` 1MiB 안). 키 경로는
  `DW_APS_ZSTD_KEY_FILE`; 없으면 `aps_zstd_key_unset` 경고 한 번, 평문은 계속 푼다.
- **의존성** `zstandard`, `cryptography`. 순수 Python AES는 블록당 0.2 ms라 resync 스캔에 느렸다. `uv add`는
  돌고 있는 `dw-collector.exe`를 못 지워 실패하고 pyproject를 되돌렸다 — `uv add --no-sync` 뒤
