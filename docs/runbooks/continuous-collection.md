# 상시 수집

**이 문서에서 검증된 것과 안 된 것을 먼저 밝힌다.** 대시보드의 `Real-time
sync` 표시는 로컬 스택에서 양쪽 상태 모두 확인했다. 좌표는 기기마다 다르므로
아래에 좌표를 **적어 두지 않았다.** 지어낸 좌표가 든 스크립트는 없는 것보다
나쁘다.

**2026-08-03에 라이브 캡처와 ADB 순회를 Windows에서 처음 돌렸다.** 결과는
아래 「2026-08-03에 실제로 돌려보고 알게 된 것」에 있다. 요약하면 캡처·가드·
sync는 동작했고, **로스터·랭킹 보드 커맨드는 아직 라이브로 한 번도 못 받았다.**

## 2026-08-03에 실제로 돌려보고 알게 된 것

### 1. 캡처 인터페이스는 반드시 `\Device\NPF_{GUID}` 형태로 적는다

`DW_CAPTURE_INTERFACE`에 어댑터의 표시 이름을 적었더니(이 머신은 `이더넷`)
**캡처가 조용히 0건을 잡았다.** scapy는 모르는 인터페이스에 대해 항의하지
않는다 — 그냥 아무 패킷도 안 준다. 프로세스는 살아 있고, 시작 로그도 남고,
`dw-sync` 하트비트도 계속 뛴다. 즉 **대시보드는 정상으로 보이는데 데이터만
안 들어온다.**

비워두면 scapy가 알아서 고르고 그것도 동작하지만, VPN이 올라오면 달라질 수
있으므로 장치 이름으로 고정하는 편이 낫다. GUID는 이렇게 찾는다:

```powershell
uv run python -c "from scapy.arch.windows import get_windows_if_list; [print(d['name'], d['guid']) for d in get_windows_if_list()]"
```

**코드가 이제 이걸 막는다.** 알려진 어댑터와 안 맞는 이름이면 캡처가 시작
시점에 `InterfaceNotFoundError`로 죽는다. 조용히 0건보다 시끄럽게 죽는 쪽이
무인 운영에서 항상 낫다.

**다만 인과는 관측 1회짜리다.** 표시 이름이 설정된 상태에서 같은 시간대에
pcapng probe는 커맨드 3종을 디코딩했는데 `dw-capture`는 0건이었다 — 그 한
번의 동시 비교는 유효하다. 그러나 인터페이스를 바꿀 때 **프로세스도 함께
재시작했고** 게임 트래픽 양도 달랐으므로, "표시 이름이 원인"이 확정된 것은
아니다. 검증 자체는 어느 쪽이든 옳으므로 남기되, 이 문서가 그것을 확정된
원인으로 읽히게 두지 않는다.

### 2. 화면을 여는 것만으로는 로스터가 오지 않는다 — 회선에서 확인함

**이것이 상시 수집의 유일한 남은 장애물이다.** 순회가 화면을 열어도 서버가
보드를 안 보내면 순회는 아무 값도 만들지 못한다.

연맹 화면·멤버 탭·등급 그룹 확장·스크롤·게임 재시작을 전부 해봤지만
`al.rank`가 **한 번도 안 왔다.** 처음에는 캡처를 의심했지만 아니다:

- 로그인 응답 `init`은 잡힌다. 영웅 27기가 들어 있는 큰 응답이므로 **큰
  메시지 디코딩은 정상**이다.
- 사용자가 연맹→멤버→스크롤→하위 목록 확장을 하는 **90초 동안 8680 포트
  전량을 pcapng으로 떴다. 87패킷 · 10.8KB · 커맨드 4종이 전부였다**
  (`user.syn.resident`, `push.alliance.march.create`, `push.al.sign`,
  `mori.note.draw`). 94명 로스터 응답 하나만 해도 그보다 크다.

즉 **패킷이 회선에 없다.** 수집기 코드와 무관한, 게임 클라이언트의 동작이다.
연맹 패널은 `push.alliance.*`·`push.al.*`로 들어온 것으로 화면을 그리고
있고, 전체 목록을 다시 받아오지 않는다.

**과거 8건은 어떻게 잡혔나.** 저널을 보면 `al.rank`는 단독으로 오지 않고
30ms 안에 터지는 연맹 커맨드 묶음의 일부다:

```
get.alliance.resource.store.info
alliance.reward.list
al.show.help
world.get.alliance.building
get.fortress.activity.info
get.alliance.center.point
>> al.rank
get.alliance.duel.season.info
hero.event.info.get
alliance.team.ls
```

그리고 이 묶음은 두 번 다 **`init` 약 2초 뒤**에 나온다. 화면을 여는 조작이
아니라 **접속 직후의 일괄 적재**로 보인다.

**계정 차이가 아니다 (확인함).** 본계정으로 게임을 켜고 연맹→멤버를 여는
동안 별도 저널(`probe_main.db`, 클라우드로 보내지 않음)에 캡처했다. `init`은
잡혔으니 로그인이 캡처 창 안에 있었는데, **`al.rank`도 묶음도 없었다.**
35종이 잡혔고 그중 연맹 요청 계열은 하나도 없다. 수집 계정 고유의 문제가
아니라 클라이언트 공통 동작이다.

이 결과는 "접속 시 일괄 적재" 가설도 약화시킨다 — `init`이 잡힌 세션에서
2초 뒤 묶음이 오지 않았다. **무엇이 그 묶음을 유발하는지는 여전히 모른다.**

**dumpcap으로도 안 나온다 (확인함).** 우리 스니핑(scapy)을 의심해
`dumpcap.exe`로 120초를 떴다 — 재시작·로그인·연맹·멤버 탭을 하는 동안
**544패킷, 드롭 0**(`pcap:0/dumpcap:0/flushed:0/ps_ifdrop:0`), 22종. 그중
연맹 요청 계열은 **하나도 없다.** 무손실 캡처로도 안 나오므로 수집 코드의
문제가 아니라는 것이 독립적으로 확인됐다.

## `--discover-only`는 파서가 있는 커맨드를 숨긴다 (2026-08-04)

**이 문서의 `al.rank` 관련 결론 여러 개가 이 플래그 하나 때문에 틀렸다.**
아래 절들은 조사 경위로 남겨두되 **결론으로 읽지 않는다.**

`scan-capture --discover-only`는 **정규화기가 없는 커맨드만** 기록한다.
`al.rank`·기부·아레나처럼 파서가 있는 커맨드는 집계에서 빠진다 — 로스터를
찾을 때 쓰면 안 되는 플래그인데, 찾던 것이 정확히 그 집합이었다.

같은 파일, 플래그만 다르게:

```
scan-capture --pcap darkwar_alrank.pcapng --db x.db --discover-only
  → 4종, al.rank 없음

scan-capture --pcap darkwar_alrank.pcapng --db x.db
  → ingested=1, alliance_member_snapshots 93행
```

**디코더는 멀쩡하다.** `C:\darkwar-adb\extract_darkwar_alrank.py`(표준
라이브러리만 쓰는 단독 추출기)와 **똑같이 93명**을 뽑는다. 재조립도 정상이다 —
그 파일 inbound 스트림 47세그먼트를 `pending 0, gap_skips 0`으로 완주한다.

**살아남은 관찰과 무너진 논거를 구분해 둔다.**

- **살아남음**: 오늘 dumpcap으로 뜬 두 창에는 `al.rank`가 실제로 없다. 플래그
  없이 다시 스캔해도 없다(`ab_dumpcap` 46종 중 파서 있는 것은
  `get.user.info.multi` 하나, `dumpcap_test`는 0개). 그 창에서 클라이언트가
  로스터를 요청하지 않은 것은 맞다.
- **무너짐**: "pcap에 `al.rank`가 없다"(있다 — `re-capture` 94명, `probe`
  88명), "원본 캡처가 없어졌다"(`C:\darkwar-adb`에 있다), "디코더가
  흘린다"(안 흘린다).

**40% 비교는 방향이 반대로 영향받는다.** dumpcap 쪽을 `--discover-only`로
셌으므로 **과소 집계**됐고, `dw-capture` 쪽은 저널이라 전부 셌다. 그런데도
dumpcap이 더 많이 봤다. **40%는 하한이고 실제 격차는 더 크다.**

**회귀 테스트로 고정할 값은 이미 있다** — `darkwar_alrank.pcapng`에서
`alliance_member_snapshots` 93행. 파일 자체는 저장소에 넣지 않는다(`.pcapng`는
gitignore 대상이고 UID·세션 서명이 들어 있다). 살균 fixture를 만드는 것이 이
저장소의 방식이다.

### `dw-capture` 유실 — 고쳤다 (2026-08-04)

**원인은 스니핑 루프 안에서 저널까지 쓴 것이었다.** scapy의 `prn` 콜백이
디코딩과 SQLite 트랜잭션을 그 자리에서 처리하는 동안 Npcap 링 버퍼를 아무도
안 읽었고, 버스트가 드라이버 단에서 버려졌다. **그 유실은 어디에도 보고되지
않는다.**

먼저 범위를 갈랐다. 같은 pcapng을 라이브 세션 경로와 오프라인 경로에 각각
흘리니 **결과가 완전히 일치했다**(638건, 46종, 불일치 0). 재조립도 디코더도
무죄이고, 남는 것은 패킷 공급뿐이었다.

`SegmentPump`를 넣었다 — 콜백은 큐에 넣기만 하고 워커 스레드가 저널에 쓴다.
같은 방식으로 다시 재니:

| | 수정 전 | 수정 후 |
|---|---|---|
| 커맨드 종류 | dumpcap 45 대 **27** | dumpcap 42 대 **42** |
| 관측 | 636 대 **387** | 1,357 대 **1,305** |
| 통째로 놓친 종류 | **18종** | **0종** |

남은 52건(3.8%)은 경계 효과로 보인다. dumpcap은 `duration:150`으로 스스로
끝나고 `dw-capture`는 그 몇 초 뒤에 종료되므로 두 창이 정확히 겹치지 않는다.

**설계에서 신경 쓴 것 셋.** 큐가 차면 **버리지 않고 막는다**(여기서 버리면
잴 수 있는 유실을 잴 수 없는 유실로 바꾸는 셈이다). `close()`가 큐 잔량을
다 쓴 뒤 반환한다(안 그러면 유실이 매 실행 끝으로 옮겨갈 뿐이다). 워커 예외를
삼키지 않고 다시 던진다.

**마지막 것이 첫 실행에서 값을 했다.** SQLite 연결은 스레드를 넘길 수 없는데
저널을 메인에서 만들고 워커에서 썼다. 조용히 0건이 되는 대신 즉시 터졌다.
`Journal(path, single_writer_thread=True)` 옵트인으로 고쳤고 **기본값은 엄격히
남겼다** — writer가 하나 더 생기면 조용한 손상 대신 큰 에러가 나야 한다.

### `dw-capture`가 재접속 뒤 영구히 멈춘다 — 고쳤다 (2026-08-04)

**증상**: 프로세스는 살아 있고, 에러도 없고, `dw-sync` 하트비트도 계속 뛴다.
그런데 저널이 자라지 않는다. 즉 **대시보드는 정상으로 보이는데 데이터만 안
들어온다.**

**멈추는 시점이 정확하다 — 게임이 재접속할 때다.**

```
init      04:08:42, 04:15:38
마지막 관측 04:15:38   ← 두 번째 로그인 버스트
그 뒤 253초 동안 저널 0건 증가
같은 시간 회선에는 15초에 68패킷 / 18KB가 흐름
```

마지막 8건이 전부 로그인 버스트다(`check.device.change`,
`push.refresh.hero.lottery`, `change.user.parseid`, `push.setting` …). **새
연결은 잡혔고 버스트도 디코딩됐다.** 그 직후부터 아무것도 안 나온다.

**원인은 `MAX_FRAME_SIZE`였다 — 고쳤다 (2026-08-04).**

추정은 반쯤 맞았다. 디코더가 잘못된 길이를 기다리며 그 뒤 바이트를 전부
본문으로 삼키는 것은 맞다. 그러나 **"상한도 resync도 없다"고 적은 것은 틀렸다.**
둘 다 있었다 — `MAX_FRAME_SIZE` 상한과 바이트 단위 resync 모두.

문제는 상한의 **값**이었다. 32MB다. 그리고 상한은 "말도 안 되는 값을 거부하는
것"만이 아니라 **하나의 가짜 헤더가 스트림을 얼마나 오래 가릴 수 있는지**를
정한다. 상한 아래를 주장하는 가짜 길이는 거부되지 않고 **기다려진다.** 초당
수 KB가 흐르는 회선에서 32MB를 기다리는 것은 영원이다.

실측으로 값을 정했다. 캡처 12개(로그인·로스터·아레나·연맹 랭킹·플레이어
프로필 + 이틀치 라이브)의 프레임 **4,906개**:

| 크기 | 개수 |
|---|---|
| <1KB | 4,126 |
| <8KB | 742 |
| <64KB | 34 |
| <256KB | 4 |
| ≥256KB | **0** |

최대는 **83,549바이트**(로그인 응답). 상한을 **1MiB**로 내렸다 — 실측 최대의
12배 여유, 그리고 최악의 대기가 32MB가 아니라 1MiB치 트래픽이다.

회귀 테스트는 동작이 아니라 **숫자**를 고정한다(`test_frame_stall.py`). 상한을
32MB로 되돌리면 실패한다. 실 캡처 넷을 다시 스캔해 디코딩이 그대로인 것도
확인했다.

**오늘 이것을 두 번 잘못 짚었다.** 처음에는 인터페이스 이름 탓으로 봤는데,
고칠 때마다 프로세스를 재시작해서 나아 보였을 뿐이다. 재시작이 유일하게
효과가 있었던 이유가 이것이다.

**펌프와는 별개다.** 펌프(관측 40% 유실)는 고쳐졌고 측정으로 확인했다. 이
멈춤은 그 위에 남아 있다.

### 상한을 내려도 멈춤은 그대로다 — 라이브에서 확인 (2026-08-04)

**정정한다.** 1MiB로 내린 뒤 라이브에서 재현했더니 **여전히 멈춘다.**

같은 120초 창에서:

| | 결과 |
|---|---|
| dumpcap | 291패킷 드롭 0, 이벤트 78건, 24종 |
| `dw-capture` | 관측 10 → **10** (증가 0) |

연맹 멤버를 열어 트래픽이 확실히 흐르는 창이었다. 그리고 증상이 문서에 적힌
것과도 다르다 — **시작 5초 만에 멈췄다.** "두 번째 재접속에서"가 아니다.

상한 가설이 완전히 틀린 것은 아닐 수 있다. 1MiB라도 20초에 378바이트가
흐르는 유휴 회선에서는 **15시간**이 걸린다. 대기를 "영원"에서 "아주 오래"로
줄였을 뿐일 수 있다. 그렇다면 **바이트가 아니라 시간으로 끊어야 한다.**
그러나 다른 후보도 남아 있다 — 장시간 돌던 scapy가 배달을 멈췄을 가능성, 펌프.
**지금 근거로는 못 가른다.**

상한 자체는 되돌리지 않는다. 32MB는 실측 최대(83,549바이트)의 400배로 어차피
부적절했고, 테스트도 유효하다. 다만 **"이걸로 멈춤이 고쳐졌다"는 주장은
틀렸다.**

### `capture.health` — 이제 어느 쪽인지 로그가 말한다

멈춤을 세 번 다 잘못 짚은 이유는 밖에서 보면 전부 똑같아서다: 살아 있고,
에러 없고, 하트비트 뛰고, 저널만 안 자란다. 통계는 정상 종료에만 있었는데
작업 스케줄러는 죽이지 실행을 중단시키지 않으므로 **아무도 본 적이 없다.**

`dw-capture`가 이제 주기적으로(`DW_CAPTURE_HEALTH_SECONDS`, 기본 60초) 찍는다:

```
capture.health  segments=35 frames=27 buffered_bytes=3993 pending_segments=0
                pump_pending=0 resync_bytes=10 last_frame_at=...
```

판독법:

| 지표 | 뜻 |
|---|---|
| `segments`가 안 늘어남 | **패킷이 안 들어온다** — 인터페이스 또는 scapy |
| `segments`는 늘고 `frames` 정체 + `buffered_bytes` 계속 증가 | **디코더가 오지 않을 길이를 기다린다** |
| `pump_pending`이 계속 큼 | **저널 쓰기가 못 따라간다** |

`buffered_bytes`가 몇 KB인 것은 정상이다 — 프레임 중간에서 창이 끊긴 것이고
다음 세그먼트로 완성된다. **계속 커지는 것**이 문제다.

**멈춤은 간헐적이다.** 계측을 붙이고 다시 띄웠을 때는 40초 넘게 정상이었다.
방아쇠가 무엇인지 아직 모르고, 다음에 멈추면 위 로그가 답을 준다.

그때까지 운영은 dumpcap + `ingest-dir` 경로를 쓴다(이 문서 맨 위). 그 경로는
파일마다 디코더가 새로 생기므로 이 버그의 영향을 애초에 안 받는다.

### 시계 — 지금은 맞지만 아무도 맞춰주지 않는다

세션 로그에 `capture.clock_skew`가 여러 번 찍혔다(**-91.8초, -300.4초,
-118.4초**). 처음에는 이 머신의 시계가 틀린 것으로 읽었는데 **아니다.**

**시스템 시계는 정확하다.** 독립적인 두 출처의 HTTP `Date` 헤더와 대조해
1초 이내다(Supabase -0.7초, Google -0.2초). 즉 `captured_at`은 믿을 수 있고,
"5분 오차로 01:59 경계를 잘못 읽는다"는 우려는 **근거가 없었다.**

`skew_seconds`는 **게임 서버가 스스로 보고한 시각**과 우리 시각을 비교한다
(`clock.py`). 그러므로 음수 skew는 서버 쪽 값이 뒤처져 있다는 뜻이다. 그리고
그 필드는 모듈 주석이 밝혀둔 대로 **단일 샘플에서 의미를 추정한 것**이라
(`db_timezone_offset`이라는 이름에 epoch가 들어 있다) 값 자체를 신뢰 근거로
쓰기 이르다. -91에서 -300까지 흔들리는 것은 서버가 값을 찍은 시점과 push가
도착한 시점의 간격일 수 있다. **샘플이 더 필요하다.**

**진짜 위험은 다른 곳에 있다. Windows Time 서비스가 꺼져 있다:**

```
Get-Service w32time  →  Status: Stopped,  StartType: Manual
w32tm /query /status →  The service has not been started. (0x80070426)
```

지금 맞는 것은 우연이고, **드리프트를 되돌릴 장치가 없다.** 무인으로 몇 주
돌리면 조용히 벌어진다. 등급 산정이 일요일 01:59 UTC 경계에 1분 단위로 걸려
있으므로, **상시 운영 전에 시간 동기화를 켜 두어야 한다.** 시스템 설정이므로
사람이 직접 한다(관리자 PowerShell):

```powershell
Set-Service w32time -StartupType Automatic
Start-Service w32time
w32tm /resync
```

캡처가 시계를 고치지 않고 경고만 남기는 것은 옳은 설계다 — 이 프로세스가
시스템 시계를 만질 일이 아니고, 잘못된 시계로 돈 세션은 나중에 알아볼 수
있어야 한다.

### (수정 전 기록) `dw-capture`는 관측의 40%를 잃는다 — 통제된 비교로 확인

**같은 창에서 dumpcap과 `dw-capture`를 동시에 돌렸다.** 같은 인터페이스, 같은
BPF 필터, 같은 150초. 차이는 캡처 방식뿐이다.

| | dumpcap | `dw-capture` |
|---|---|---|
| 패킷 | 1,683 (드롭 0) | — |
| 커맨드 종류 | **45** | **27** |
| 관측 합계 | **636** | **387** |

**18종은 통째로 못 봤다**: `world.get.new`(28→0),
`push.world.march.world.get.new`(28→0), `push.alliance.march.create`(10→0),
`get.server.world.info`(6→0), `world.get.alliance.city.effect`(6→0),
`stat.tt`(4→0), `train.list`(2→0), `push.mail`(1→0) 외.

잡은 것들도 대체로 절반 안팎이다 — `push.al.help.update` 60→19,
`push.alliance.march.refresh` 74→48, `push.al.sign` 10→4, `player.info` 5→1.
`push.battle.round.batch`만 65→64로 거의 온전한데, 왜 이 커맨드만 다른지는
모른다.

**원인은 아직 규명하지 않았다.** 유력한 가설은 `sniff(prn=...)`가 패킷마다
Python 콜백을 태우므로 Npcap 링 버퍼가 버스트에서 넘친다는 것이다. 그러나
"거의 절반"이라는 규칙성은 단순 버퍼 오버런보다는 다른 무언가를 시사한다 —
한쪽 방향만 처리한다거나, 재조립이 특정 조건에서 스트림을 버린다거나. **재현
절차가 있으므로**(`scratchpad`의 `ab_capture.ps1` 방식) 다음 세션이 계측부터
다시 할 수 있다.

**이것이 상시 수집에 갖는 의미는 크다.** 40%를 잃는 수집기는 등급 리포트의
입력을 조용히 갉아먹는다. 그리고 그 손실은 화면에 "캡처 없음"이 아니라 **낮은
점수**로 나타난다 — 일요일 01:59 창에서 우려한 것과 같은 실패 양상이다.

**바꿀 길은 이미 열려 있다.** `CLAUDE.md`가 "라이브 캡처는 `Observation`의 한
생산자일 뿐"이라고 정해 둔 덕분에, **dumpcap이 링 버퍼로 pcapng을 쓰고
`scan-capture`가 이어받는** 구조가 새 설계가 아니라 이미 검증된 경로다.
유실도 dumpcap이 카운터로 보고한다. 재현 명령:

```powershell
& "C:\Program Files\Wireshark\dumpcap.exe" -i \Device\NPF_{GUID} `
    -f "tcp port 8680" -w out.pcapng -a duration:150 -B 64
uv run dw-collector scan-capture --pcap out.pcapng --db scan.db --discover-only
```

**다만 로스터 문제는 이것으로 설명되지 않는다.** 드롭 0인 dumpcap 창에서도
`al.rank`와 연맹 묶음은 나오지 않았다. 두 문제는 별개다.

**한 가지 주의.** `dw-capture`는 인터페이스 전체를 듣는다. BlueStacks
인스턴스를 두 개 돌리면 **두 계정의 트래픽이 같은 저널에 섞인다** — 저널은
`collector_id`로 출처를 새기므로 섞이면 되돌릴 수 없다. 진단 목적으로 다른
계정을 캡처할 때는 반드시 `DW_SQLITE_PATH`를 따로 주고 sync하지 않는다.

**이 가설이 맞으면 순회 설계가 바뀐다.** 탭만으로는 보드를 못 받으므로
routine이 재접속을 포함해야 하는데, `am force-stop`·`am start`는 가드가
차단 목록에 넣어둔 명령이다(본계정 오조작 방지, FR-COL-010). 그 결정을
뒤집는 것이 아니라, 수집 인스턴스에 한해 허용하는 별도 경로가 필요한지
판단해야 한다. **먼저 가설을 확인하고 나서 결정한다.**

### 3. `dw-capture`는 정상 종료에서만 통계를 남긴다

`session.stats`(재동기화 바이트·gap·거부 수)는 `finally`에서 로그로 나간다.
작업 스케줄러가 프로세스를 죽이면 그 블록이 안 돌아 **진단에 필요한 값이
사라진다.** Windows에서 백그라운드 프로세스에 Ctrl+C를 보내는 깔끔한 방법이
없으므로, 무인 운영에서는 통계를 주기적으로 남기거나 저널에 적는 편이 낫다.
아직 안 고쳤다.

## 지금 돌리는 방법 (2026-08-04, 실제로 등록해서 돌림)

**`dw-capture`를 쓰지 않는다.** 그것은 프로세스 수명 내내 재조립기를 하나만
쓰므로, 스트림이 한 번 꼬이면 조용히 멈추고 살아 있는 것처럼 보인다(아래
「재접속 뒤 영구히 멈춘다」). dumpcap이 파일을 쓰고 `ingest-dir`가 읽는다 —
파일마다 재조립기가 새로 생기므로 그 고장이 **한 파일로 갇힌다.**

네 프로세스를 작업 스케줄러에 **로그온 시 실행**으로 건다. 서비스가 아닌
이유는 BlueStacks와 Npcap 캡처 둘 다 데스크톱 세션이 필요해서다.

| 작업 | 명령 |
|---|---|
| `DarkWar-Capture` | `dumpcap -i <NPF> -f "tcp port 8680" -w C:\DW_data\live\cap.pcapng -b duration:60 -b files:1440 -B 64` |
| `DarkWar-Ingest` | `uv run --no-sync dw-collector ingest-dir --dir C:\DW_data\live --min-age-seconds 20 --interval-seconds 30` |
| `DarkWar-Sync` | `uv run --no-sync dw-sync` (`DW_SYNC_BATCH_SIZE=1000`) |
| `DarkWar-Notify` | `uv run --no-sync dw-notify` (`DW_NOTIFY_INTERVAL_SECONDS=300` 기본) |

**`DarkWar-Notify`는 2026-08-09까지 아예 등록돼 있지 않았다.** 그래서 공지든
가이드든 발행해도 디스코드에 아무것도 안 갔다. 이 프로세스 하나가 "무엇을
알릴지 계산"과 "실제로 POST" 두 몫을 다 하기 때문에, 없으면 아웃박스가
채워지지도 비워지지도 않는다. 설정 화면의 **Send test** 버튼도 아웃박스에
행만 넣으므로 같이 안 갔고, 그래서 증상이 웹훅·라우팅 문제처럼 보였다.

1분짜리 파일 1440개 = 24시간치. 등록 스크립트는 이제 저장소에 있다 —
[`scripts/windows/register-tasks.ps1`](../../scripts/windows/register-tasks.ps1).
**관리자 PowerShell**이 필요하다(작업 등록은 권한이 있어야 한다).

한 번이라도 등록된 머신에서는 `-Interface`가 선택이다 — 스크립트가 자기가 쓴
`run-Capture.cmd`에서 NPF 장치명을 다시 읽어, 지금 캡처가 물려 있는 어댑터를
그대로 유지한다. `dumpcap -D`에서 새로 고르다 틀리면 캡처가 **조용히** 아무것도
안 받는다(작업은 `Running`, 로그도 조용). 바꿀 때만 명시적으로 넘긴다.

```powershell
.\scripts\windows\register-tasks.ps1 -Interface '\Device\NPF_{...}'
```

인터페이스는 `& 'C:\Program Files\Wireshark\dumpcap.exe' -D`로 찾거나
`DW_CAPTURE_NPF_DEVICE`에 넣어 둔다. 스크립트가 등록까지 하고 **띄운 다음 10초
뒤에 정말 `Running`인지 확인한다** — 아래 「uv가 자기 발등을 찍는다」가 정확히
"시작은 성공했는데 돌지 않는" 모양이었기 때문이다.

작업 설정에 넣은 것: 로그온 트리거 + **5분 반복(3650일)**, 실패 시 1분 간격
재시작, **실행 시간 제한 없음**(기본값은 3일 뒤 죽인다), 중복 실행 방지,
배터리에서도 계속. 되살리는 것은 반복 트리거다 — 재시작 설정은 종료 코드가 0이
아닐 때만 걸리고, 여기서 죽는 방식은 대체로 0을 남긴다.

### `uv`가 자기 발등을 찍는다 — 2026-08-07 사고의 원인

`DarkWar-Ingest`가 `Ready`인 채로 몇 시간 있었고 outbox가 **288,471행**까지
밀렸다. 5분 반복 트리거는 정상 작동 중이었다. 매번 살아나서 1초 안에 죽고
있었을 뿐이다. `ingest.log`에 320줄:

```
error: failed to remove file `...\.venv\Lib\site-packages\../../Scripts/dw-sync.exe`:
The process cannot access the file because it is being used by another process. (os error 32)
```

**`uv run`은 실행 전에 프로젝트 환경을 재동기화하고, 동기화는
`.venv\Scripts`의 콘솔 스크립트를 다시 쓴다.** 상시 실행 중인 `dw-sync`가
자기 `dw-sync.exe`를 잡고 있으니, 같은 프로젝트 디렉터리를 쓰는 ingest는
**sync가 살아 있는 한 절대 못 뜬다.** 간헐적 고장이 아니라 영구 고장이다.

고친 방법은 `uv run --no-sync`다. 의존성 설치는 스케줄된 작업이 몰래 할 일이
아니다 — 환경 동기화는 register 스크립트가 **전부 멈춘 그 순간에 한 번** 한다.
의존성을 바꿨으면 register 스크립트를 다시 돌린다.

**같이 드러난 것**: `run-hidden.vbs`가 자식의 종료 코드를 버리고 있어서
(`shell.Run` 반환값 미사용) wscript가 0으로 끝났다. 그래서 이 실패가
`LastTaskResult=0`, 즉 성공으로 보였다. 지금은 `WScript.Quit code`로 올린다.
반복 트리거가 없었다면 이 하나로 무기한 정지였을 것이다.

**진단할 때 헷갈리는 코드 둘**:

| 코드 | 뜻 |
|---|---|
| `0x800710E0` | 실행 중이라 `IgnoreNew`가 반복 실행을 거절했다 — **정상** |
| `0x0` + `Ready` | 방금 죽었을 수도 있다. 로그를 봐야 한다 |

**확인 방법**

```powershell
Get-ScheduledTask -TaskName "DarkWar-*" | ForEach-Object {
    "$($_.TaskName) $($_.State) $((Get-ScheduledTaskInfo $_.TaskName).LastTaskResult)" }
uv run dw-collector journal-summary --db C:\DW_data\live.db
```

**셋 다 `Running`이어야 한다.** 저널의 `ingested_captures`에 파일이 쌓이고
`sync_outbox`의 pending이 0에 가까우면 끝까지 도는 것이다. 첫 파일은
1분 창이 끝나고 20초가 더 지나야 들어온다 — `--min-age-seconds`가 아직 쓰이는
중인 파일을 건드리지 않게 막는다. 최악 지연은 60+20+30 = **110초**.

`Running`만으로는 부족하다. 진짜 물어야 할 것은 **ingest가 따라잡고 있는가**다:

```powershell
Get-ChildItem C:\DW_data\live\cap_*.pcapng | Sort-Object Name | Select-Object -Last 1
uv run --no-sync dw-collector journal-summary --db C:\DW_data\live.db
```

마지막 캡처 파일 번호와 저널의 마지막 ingest 파일 번호 차이가 **2~3을 넘어서
계속 벌어지면** ingest가 죽었거나 못 따라가는 것이다. pending이 단조 증가하는
것도 같은 신호다.

**전원 설정을 확인한다.** 절전이나 최대 절전으로 들어가면 새벽 수집이 끊기고,
그게 하필 일요일 01:59 UTC 창이면 등급 리포트가 통째로 틀어진다.

**남은 것은 ADB 순회다.** 위 셋은 화면을 열지 않는다 — 사람이 게임을 하는 동안
흐르는 트래픽만 줍는다. 순회가 붙어야 무인이 된다. 그리고 순회를 짜려면 먼저
로스터를 무엇이 유발하는지 알아야 한다(아래).

## 무엇이 상시로 돌아야 하나

세 가지가 동시에 살아 있어야 한다.

| 프로세스 | 하는 일 | 없으면 |
|---|---|---|
| `dw-capture` | 게임 트래픽을 저널에 적는다 | 새 관측이 없다 |
| `dw-sync` | 저널을 Supabase로 보내고 **10초마다 하트비트** | 대시보드가 안 갱신되고 `Real-time sync stopped` |
| ADB 순회 | 게임 화면을 열어 응답을 발생시킨다 | 수집기는 살아 있는데 볼 것이 없다 |

세 번째가 핵심이다. **수집기는 수동 스니퍼다** — 요청을 보내지 않고, 게임이
이미 받은 응답만 해독한다. 화면을 아무도 열지 않으면 랭킹도 로스터도 오지
않는다.

## 대시보드 표시

`dw-sync`가 하트비트를 쓰고, 뷰 `public.sync_status`가 그것 하나만 노출한다.
**1분간 하트비트가 없으면 `Real-time sync stopped`.** dw-sync는 10초마다
보내므로 여섯 번을 놓쳐야 꺼진 것으로 본다 — 왕복이 느린 순간에 깜빡이지 않을
만큼 길고, 보는 사람이 알아챌 만큼 짧다.

임계값은 **뷰 안에** 있다. 대시보드에 두면 "살아 있다"가 두 뜻을 갖게 된다.

`collectors`와 `collector_heartbeats`는 여전히 officer 이상 전용이다. 버전·
outbox 깊이·패킷 나이는 운영 정보다. 노출되는 것은 **마지막 하트비트 시각 하나**
뿐이고, 그건 스냅샷의 `captured_at`이 이미 말하고 있는 것이다.

## 순회가 반드시 돌아야 하는 시각

등급 리포트의 정확도가 여기 달려 있다. 이 시각들에 캡처가 없으면 **화면에
"캡처 없음"이 아니라 낮은 점수로** 나타난다.

| 시각 (UTC) | 열 화면 | 왜 |
|---|---|---|
| **일 01:59** | 연맹 기부, 듀얼 주간 | 02:00에 게임이 주간 보드를 비운다. **1분 늦으면 전원 0점** |
| **월 02:00** | 서버 랭킹(전투력) | 2주 기간의 경계 |
| **매일 02:05** | 서버 랭킹(전투력) | 멤버 페이지 Growth 열의 기준 시점 |
| **매일 아무 때나** | 연맹 기부 **일간**, 연맹 전투 **일간** | 일간 보드는 02:00에 리셋된다. 그날 안에 안 읽으면 그 하루는 영구히 없다 |

나머지 화면(아레나, 연맹 로스터, 크로스서버 보드)은 아무 때나, 자주 돌수록
좋다.

### 실제로 놓쳤다 — 이게 어떻게 보이는지 (2026-08-06)

08-03 기간(08-03 ~ 08-17)을 08-06에 빌드했을 때 `week2`가 null이었고, 그 전에는
`week1`도 null이었다. 그동안 등급은 **presence와 전투력 성장만으로** 결정됐다.
화면에는 "기여도 없음"이 아니라 그냥 낮은 등급으로 나온다.

week1은 08-06에 누군가 게임을 하다 보드를 열어서 채워졌다 — 실측으로 기부 44,680 /
듀얼 2,239,192 같은 값이 들어왔다. **우연이었고, 이것이 스케줄러가 필요한 이유다.**

주간 측정 시점은 진행 중 기간에서도 "그 시점 이전의 가장 최근 읽기"를 쓴다. 즉
**기간 안에서 일찍 읽어 두면 없는 것보다 낫다** — 08-06 캡처가 08-10 측정점의
week1 값으로 채택된 것이 그 예다. 늦게 읽는 것만이 되돌릴 수 없다.

### 일간 보드는 누적되고, 리셋된다 — 하루에 여러 번 읽는 편이 낫다

`alliance_daily_contribution`(0074)은 하루 총합을 **그날 최댓값**으로 잡는다.
보드가 하루 동안 쌓이기 때문이다. 08-05는 4번 읽혔고 43M → 46M → 52M → 137M로
올라갔다. 한 번만, 이른 시각에 읽으면 그 하루는 **부분 합**이고 화면에서 "그날
연맹이 놀았다"처럼 보인다.

뷰가 `readings`를 같이 내보내고 추이 화면이 "한 번만 읽은 날 N개"라고 쓴다.
그 문구가 보이면 스케줄이 부족한 것이다.

## ADB 순회를 만드는 법

BlueStacks는 ADB로 붙는다. `CLAUDE.md`가 말하는 "캡처·BlueStacks·ADB는 한
프로세스 트리"가 이 얘기다.

```powershell
adb connect 127.0.0.1:5555
adb devices
```

좌표는 **직접 찾아야 한다.** 해상도마다 다르고, 게임 업데이트로 옮겨간다.

```powershell
# 지금 화면을 받아서 좌표를 읽는다
adb exec-out screencap -p > screen.png
# 눌러 보고 맞는지 확인한다
adb shell input tap 540 1200
```

한 화면씩 좌표를 확정해 목록으로 적어 두고, 그 목록을 순서대로 재생하는
스크립트를 쓴다. **화면 전환은 기다려야 한다** — 응답이 도착하기 전에 다음
탭을 보내면 그 화면은 열리지 않은 채로 지나간다.

순회가 한 바퀴 돌 때마다 `dw-capture`가 응답을 줍는다. 확인은 저널로 한다:

```powershell
uv run dw-collector journal-summary
```

명령별 관측 수가 늘어나면 순회가 실제로 화면을 열고 있는 것이다.

## 꺼졌다 켜질 때

데이터 쪽은 특별히 할 일이 없게 만들어 두었다.

- 저널은 SQLite 파일이라 프로세스가 죽어도 남는다.
- `dw-sync`는 다시 뜨면 밀린 outbox부터 비운다.
- 대시보드는 **마지막으로 받은 값을 계속 보여주고** 배지만
  `Real-time sync stopped`로 바뀐다. 데이터가 사라지지 않는다.
- 파서가 좋아진 뒤라면 `dw-collector renormalize`로 **원본 관측을 지금 파서로
  다시** 돌릴 수 있다. idempotency_key가 원본 payload를 해시하므로(§11.2)
  다시 sync해도 중복이 아니라 갱신이다.

**그런데 그것은 프로세스가 다시 뜬 다음의 얘기다.** 정전으로 머신이 꺼졌다
켜지면 네 작업은 전부 **로그온 시 실행**이라 아무것도 안 뜬다. 실제로 그렇게
됐다 — 전기는 돌아왔고 컴퓨터는 잠금 화면에 앉아 있었다.

### 정전 뒤 스스로 돌아오게 하는 세 가지

셋 다 필요하고, 소프트웨어로 되는 것은 하나뿐이다.

1. **BIOS: Restore on AC Power Loss = Power On.** 이게 없으면 머신은 그냥
   꺼져 있다. 코드로 고칠 수 있는 문제가 아니다.
2. **Windows 자동 로그온** (`netplwiz` 또는 Sysinternals Autologon). 로그온이
   없으면 트리거가 안 걸린다. 작업이 서비스가 아닌 이유는 위에 적어 뒀다 —
   BlueStacks와 Npcap 캡처 둘 다 데스크톱 세션이 필요하다.
3. **`DarkWar-ColdStart` 작업.** 게임을 열고, 로그인 팝업을 닫고, 필드로
   나간다. 등록은
   [`scripts/windows/register-cold-start.ps1`](../../scripts/windows/register-cold-start.ps1).

### 콜드 스타트는 반복 트리거가 없다

나머지 네 작업과 정반대다. 그것들은 죽으면 5분 반복 트리거가 되살리는
장기 실행 프로세스다. 이것은 **좌표를 탭한다.** 5분마다 돌면 아무도 안 보는
머신에서 게임 화면에 좌표를 계속 눌러댄다. 그래서 로그온에 한 번만 걸고,
`register-tasks.ps1`의 검사 루프는 반대로 "반복 트리거가 **있어야** 한다"를
못 박는다. 규칙이 반대라서 파일을 나눴다. 한 파일에 예외를 두지 않는다.

### 좌표는 여전히 저장소에 없다

`services/collector/routines/example-cold-start.json`이 템플릿이고, 좌표는
0, 패키지는 `com.example.replace.me`다. 실물은 `C:\DW_data\routines\`에 둔다.
등록 스크립트는 **템플릿 패키지가 남아 있으면 등록을 거부한다** — 좌표 0을
누르는 콜드 스타트는 없느니만 못하다. 성공했다고 보고하기 때문이다.

패키지명 찾는 법:

```powershell
adb -s $env:DW_ADB_COLLECTOR_SERIAL shell pm list packages
```

좌표는 `dw-ui-worker screenshot`으로 읽는다. 등록 전에 반드시 한 번:

```powershell
uv run dw-ui-worker run --routine C:\DW_data\routines\cold-start.json --dry-run
```

### 검증되지 않은 부분 — 읽고 넘어가지 말 것

**팝업 닫기와 필드 이동 단계는 `expect`가 없다.** 팝업을 닫거나 카메라를
움직이는 것은 회선에 아무 응답도 만들지 않으므로 러너가 기다릴 대상이
없다. 증명되는 것은 **실행 단계 하나뿐**이고, 그것은 로그인 응답 `init`이
도착하는 것으로 증명된다.

즉 팝업 개수나 위치가 바뀌면 **콜드 스타트는 여전히 `ok`를 보고하고**, 그
다음에 도는 일상 순회가 대신 실패한다. 첫 실전 콜드 스타트 뒤에는 반드시
`dw-collector journal-summary`로 실제로 값이 늘었는지 확인한다.

그리고 이 상태를 사람이 지켜보지 않아도 알 수 있게 하는 것이
[`alerting.md`](alerting.md)의 `data_stalled`다.

## 남은 위험

- **24시간 무인 운영은 게임 쪽 유휴 로그아웃이나 이용약관에 걸릴 수 있다.**
  수동 캡처 자체는 문제가 아니지만, 세션이 끊기면 순회가 빈 화면을 누른다.
  `journal-summary`가 늘지 않는 것으로 알아챌 수 있다.
- **PCAP에는 수집 계정의 UID와 세션 서명이 들어 있다.** 캡처 파일을 어디에 두는지가
  보안 경계다. `.gitignore`와 gitleaks가 둘 다 막고 있으니 약화시키지 않는다.
